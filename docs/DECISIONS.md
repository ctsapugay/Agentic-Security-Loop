# Decisions

- **Own rule engine, not Progent's code.** Progent's `secagent` uses global mutable state, `input()` prompts, and `sys.exit()`, and allows Python callables as rules. We keep its JSON-Schema argument constraints and its Z3 idea, but rules are pure data so the updater can write them and the gate can audit them.
- **Provenance at the tool-call boundary, not CaMeL's interpreter.** CaMeL's README warns that its interpreter is a research artifact that likely has bugs, and running it costs an extra planner model per task. We label each argument by where its value appears: the user prompt, a specific tool-output field, or nowhere (unknown). This gives CaMeL-style origin checks deterministically. It's weaker than full dataflow tracking: a value the model transforms becomes "unknown", which fails closed.
- **Labeling config = named source groups.** Labels are field-level (e.g. `get_most_recent_transactions:subject`), so rules can trust a bank-generated `recipient` field while distrusting an attacker-writable `subject` field.
- **Absent arguments are unconstrained** (Progent semantics), so optional arguments like `update_scheduled_transaction.recipient` don't break rules.
- **ask_user in live runs:** approved in benign episodes (counted as a confirmation) and declined when an injection is present. This models an attentive user; confirmations are reported as the usability cost.
- **Agent model:** gpt-4o-mini via OpenRouter. It's cheap, widely studied on AgentDojo, and vulnerable enough to give the loop something to learn from.
- **v1 attack source = AgentDojo's built-in attacks (human-approved, 2026-10-16).** Writing an LLM attacker that generates new injections was stopped in this build session. The human approved using AgentDojo's published attack templates for v1. The adaptive LLM attacker becomes next-phase work, built separately and plugged into the attack-source interface. Families: `important_instructions` (all variants plus `tool_knowledge`, which share one template), `ignore_previous`, `direct` → train; `system_message`, `injecagent` → held-out. GOAL.md, the gate, and the vision were updated to match (white-box results and the refusal probe move to the next phase).
- **Agent model: qwen3-235b-a22b-2507 (via OpenRouter), chosen by data.** `policyforge.agent_probe` ran 4 cheap models undefended on the same 24 built-in attacks and 16 benign tasks (`results/agent_probe.json`): gpt-4o-mini 29% attack success / 0.50 utility, gpt-4.1-mini 33% / 0.63, qwen3-235b 29% / 0.69, deepseek-v4-flash 4% / 0.63. We need an agent that both works and is attackable (otherwise the loop has nothing to learn from), so qwen3-235b wins, and it's also cheaper. Built-in templates that name the target model are filled with the gpt-4o-mini name for all candidates, so comparisons stay consistent.
- **Policy loops learn from observe-mode traces, replayed offline.** Each round's attacks run once with nothing blocked, recording what the agent *tries*. Whether an attack succeeds under a candidate rule set is decided by replaying that trace through the rules and AgentDojo's own success check. This makes validation deterministic and free, and lets E and F share one trace bank. Limitation: after a block, a live agent might try a different route; the final live evaluation (enforce mode) measures that.
- **Train-family evaluation uses fresh attacks.** Loop attacks and evaluation attacks are disjoint (user task × injection goal × template) combinations, so train_asr isn't trivially zero.
- **Prompt baseline (B) validates live, with a relative utility floor.** Prompts can't be replayed, so B re-runs past successful attacks live, and requires benign utility to stay within 0.10 of the undefended prompt's utility. (The agent's own live utility is below 0.8, so an absolute floor would reject everything.)
- **Confirmation budget: at most 0.5 user confirmations per benign task**, so the loop can't "solve" security by asking the user about everything.
